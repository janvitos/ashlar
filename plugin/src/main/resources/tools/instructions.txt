Ashlar: tools for reading and building in a live Minecraft (Paper) server. Sixteen tools are available - load them by name when needed:

mc_status   - server/plugin health and queue length
mc_players  - online players with position, eye, facing and look direction ("here", "in front of me", "at my feet")
mc_survey   - terrain survey of an x/z area: heightmap image plus exact numbers (min/max/median height, surface mix, largest flat zone); format:"text" for an ASCII map
mc_render   - one visual PNG check: isometric/perspective schematic block shapes and depth, existing top/facade/slice/heightmap views, or first-person from an eye or player
mc_sightline - can an eye or player see given blocks (visible/blocked/unknown with the first blocking block), or a coarse cone of what fills the view; read-only
mc_build    - place blocks in bulk (cuboid fills with modes replace/keep/outline/hollow/walls, individual blocks and sign text, plus rendered lettering via `text`); primary construction tool
mc_plan - validate and preview a build without placing blocks; report site collisions, overlaps, door/bed pairing and support problems
mc_verify - opt-in exact verification: prepare BEFORE building, then check frozen eligible cells; not part of routine builds
mc_repair - repair only mismatches from a fresh mc_verify comparison or mc_diff receipt, guarding stale edits/block entities
mc_blueprint - optionally generate architectural parts or fit foundations/entrances with one bounded terrain capture; save/get/list/delete reusable blueprints with named components, palettes and repeated instances; no world writes
mc_inspect  - exact block contents of a region (statistics, per-column runs, ASCII slice, sign text)
mc_diff     - compare a live box with a snapshot, expected cells/file or blueprint; differing cells, transitions, optional floating/stacked/unsupported/enclosed-air anomalies, diffId for mc_repair
mc_snapshot - save a region before changing it, list snapshots, or list/delete build journal entries (journal-list touches:{from,to} finds the calls that changed an area)
mc_restore  - roll a region back to a snapshot, or undo one journalled call cell by cell (journal), keeping later changes
mc_protect  - add/list/remove protected regions that writing tools refuse to touch (deny) or warn about without an explicit per-call override
mc_command  - run a server console command and return its output (escape hatch)

Default lightweight workflow: mc_players only when player context/safety is needed; one mc_survey before a substantial build, reusing a recent relevant survey; mc_build; one mc_render of the finished substantial build for appearance; use isometric/perspective with tight [x,y,z] bounds when an angled exterior view helps. Tiny edits can rely on build feedback. Prefer a few bulk build calls. Do not stack mc_plan, dryRun, preflight and mc_verify on ordinary builds, repeat whole-build checks, or inspect every block by default. Stop once the requested result looks satisfactory and no concrete issue remains. All builds still receive mandatory plugin-side structural safety validation, without extra agent tool calls.
If the visual check or build feedback reveals a specific issue, inspect only the affected area and make a targeted correction, with a focused recheck if needed. If it remains unresolved, explain the issue rather than starting an open-ended verification loop. Preserve rollback protection when changing existing terrain/structures: every writing mc_build, mc_repair and mc_restore returns a journal id; to undo one call later, use mc_restore {journal:"jrn-..."} (safe mode keeps cells changed since and reports them), not a whole-region snapshot restore. Snapshots remain useful to reset a whole region to one moment; prefer mc_build snapshot:true over a separate snapshot call. Journals and snapshots store block states only, not sign text or container inventories. A fresh snapshot before deletion captures current block states but does not protect that data. Do not automatically restore the whole region for a small defect. When a call is rejected for a protected region, change the plan to stay outside it; pass override:["name"] only when the user explicitly asks to change that area. mc_command is not checked against protected regions.
Coordinates: X east, Z south, Y up; from/to corners are inclusive.
For rotated or mirrored designs, mc_build accepts transform:{origin:[x,y,z],rotation:0|90|180|270,mirror:"none"|"x"|"z"}. All build coordinates then become local: mirror first, rotate clockwise viewed from above, translate last. States, partial filters and text geometry transform too. mc_plan, preflight:true and dryRun:true are optional escalation tools, not default steps. Use them when the user requests a preview/strict site checks or a concrete placement risk warrants analysis. Review pairing/support issues and existing-non-air changes; those may be terrain or structures. Do not run multiple equivalent analyses for reassurance. Planning does not reserve the world or simulate connections, fluids or entities. Isometric/perspective views use schematic visual cuboids and map colors, not textures or exhaustive resource-pack models. Stored connections are shown without updating them; approximate/fallback shapes and resolution reductions are reported. Camera azimuth/elevation are optional; fov is perspective-only and angled grids must be 0. Other views retain their existing flat maps. All build phases are structurally validated before the first snapshot/write. Reserve strict preflight for concrete pairing/support or occupied-site risks, not straightforward hull/deck fills. Understand existing controls or furnishings before removing them to satisfy preflight; a failed check is not permission to delete them.
Build execution always runs fills -> text -> individual blocks, regardless of JSON key order; array order applies within each phase. Later blocks overwrite earlier air fills. Preserve openings by omitting conflicting detail blocks or placing final air entries at the end of blocks. Build reports default to phase totals, snapshot IDs and warnings; detailed:true adds per-fill/per-text-entry results. Do not request detail routinely.

Photo-reference reconstruction: inspect supplied images first; for named structures without images, use a small useful reference set through the calling agent's image/web capabilities, or ask for images if unavailable. Ashlar does not analyze/fetch photos itself. Before placement, give a short brief: reference/front direction, supplied/documented or explicitly chosen scale anchor, approximate width:depth:height and main masses, three to five distinctive features, palette/terrain relationship, interior scope and uncertainty. Separate observed features from inferred geometry and unknown/hidden areas; do not invent measured dimensions or claim an exact unseen interior. Perspective pixel lengths are not reliable real-world dimensions. Resolve conflicting versions/views explicitly; ask only when missing information materially changes scope, scale, location or destructive edits.
Prioritize silhouette, proportions and facade rhythm before ornament. Use local transforms, reusable blueprint components and optional generators only where they fit the reference. If saving a blueprint, description/constraints can carry source links and observation/inference/unknown notes; constraints are advisory, not photographic validation. Keep the normal one-survey/build/one-render workflow, with a render viewpoint comparable to the reference and targeted corrections only. Explain schematic rendering/material approximations and unresolved uncertainty; do not invent a similarity score. Visual fidelity, including 'as close as possible', does not automatically request exact block-state auditing. mc_verify compares blocks with a frozen specification, not with a photograph.

Full exact verification is opt-in: use it only when the user explicitly requests exact block-state verification, not simply because a photo reproduction is requested, the tool is available or a build is large. Development unit/native acceptance tests are never a per-build agent workflow. When exact verification is requested, call mc_verify action:prepare with the build request BEFORE mc_build, then action:check with its planId afterward. Expectations freeze keep/filter eligibility and managed sign values; they expire after two hours or plugin reload/restart. mc_repair requires the latest comparisonId and rechecks selected observed cells before snapshot/write. It never rewrites matching cells or runs a connection/neighbor pass. Exact mode includes all properties; placement mode explicitly excludes derived connections for connected builds, never orientation or chest type. Skipped/untouched cells, entities, rich sign styling and arbitrary NBT are outside scope. Flowing plans cannot be auto-repaired. Snapshots store block states only, NOT sign text or inventories; deletion/material replacement of block entities requires explicit opt-in. Review diagnostics; this is not a world lock or transactional undo.

Saved blueprints use mc_blueprint version:1 documents with flat named components and instances. mc_build accepts blueprint:{id,palette?} instead of direct fills/blocks/text, and composes component orientation, instance position/repetition and project transform. Use $role[property=value] for material bindings. Other tools still use world coordinates. Include both door/bed halves; mirrored block lettering mirrors glyphs, not sign strings.
