Ashlar: tools for reading and building in a live Minecraft (Paper) server. Nineteen tools are available - load them by name when needed:

mc_status   - server/plugin health and queue length
mc_players  - online players with position, eye, facing and look target ("here", "in front of me", "at my feet")
mc_survey   - terrain survey of an x/z area: heightmap image plus exact numbers; format:"text" for an ASCII map
mc_render   - one visual PNG check: isometric/perspective schematic views, top/facade/slice/heightmap, or first-person
mc_sightline - can an eye or player see given blocks, or a coarse cone of the view; read-only
mc_walk     - can a player walk from A to B, or reach every door/bed/stair in a box; read-only
mc_light    - dark mob-spawn spaces in a box and optional light positions; read-only
mc_build    - primary construction tool: fills, blocks with sign text, `text` lettering, `cells`/`cellsFile`, blueprints, decorative `entities`
mc_plan     - validate and preview a build without placing blocks (collisions, overlaps, pairing, support)
mc_verify   - opt-in exact verification: prepare BEFORE building, then check; not part of routine builds
mc_repair   - repair only mismatches from a fresh mc_verify comparison or mc_diff receipt
mc_blueprint - generate parts, fit foundations/entrances, save/get/list/tag reusable blueprints; no world writes
mc_inspect  - exact block contents of a region (statistics, column runs, ASCII slice, sign text, entities)
mc_export   - write a box's blocks to a file for offline edits, mc_build cellsFile or mc_diff expectedFile
mc_diff     - compare a live box with a snapshot, expected cells/file or blueprint; diffId for mc_repair
mc_snapshot - save a region before changing it, list snapshots, list/delete build journal entries
mc_restore  - roll a region back to a snapshot, or undo one journalled call
mc_protect  - add/list/remove protected regions that writing tools refuse (deny) or warn about
mc_command  - console command escape hatch

Default lightweight workflow: mc_players only when player context/safety is needed; one mc_survey before a substantial build, reusing a recent relevant survey; mc_build; one mc_render of the finished substantial build for appearance (isometric/perspective with tight bounds when an angled view helps). Tiny edits can rely on build feedback. Prefer a few bulk build calls; do not request detailed:true routinely. Do not stack mc_plan, dryRun, preflight and mc_verify on ordinary builds, repeat whole-build checks, or inspect every block by default. mc_plan, preflight:true and dryRun:true are optional escalation for a requested preview/strict site check or a concrete placement risk; do not run equivalent analyses for reassurance. Stop once the result looks satisfactory and no concrete issue remains. All builds still receive mandatory plugin-side structural safety validation, without extra agent tool calls.
If a check reveals a specific issue, inspect only the affected area and make a targeted correction, with a focused recheck if needed; if it remains unresolved, explain it rather than starting an open-ended verification loop. Understand existing controls or furnishings before removing them to satisfy preflight; a failed check is not permission to delete them.
Preserve rollback protection when changing existing terrain/structures: every writing call returns a journal id; undo one call with mc_restore {journal:"jrn-..."}, not a whole-region restore. Prefer mc_build snapshot:true over a separate snapshot call. Journals and snapshots store block states, sign text and decorative entities (paintings, item frames, armor stands), not container inventories. Do not automatically restore a whole region for a small defect. When a call is rejected for a protected region, change the plan to stay outside it; pass override only when the user explicitly asks. mc_command is not checked against protected regions.
Coordinates: X east, Z south, Y up; from/to corners are inclusive. mc_build `transform` makes its coordinates local; other tools use world coordinates. Isometric/perspective views use schematic visual cuboids and map colors, not textures.
A blueprint build reply ends with a "Blueprint:" line (id, tags, journal id); mark progress with mc_blueprint tag (status draft/built/approved).

Photo-reference reconstruction: inspect supplied images first; for named structures without images, use a small useful reference set through the calling agent's image/web capabilities, or ask for images if unavailable. Ashlar does not analyze/fetch photos itself. Before placement, give a short brief: reference/front direction, supplied/documented or explicitly chosen scale anchor, approximate width:depth:height and main masses, three to five distinctive features, palette/terrain relationship, interior scope and uncertainty. Separate observed features from inferred geometry and unknown/hidden areas; do not invent measured dimensions or claim an exact unseen interior. Perspective pixel lengths are not reliable real-world dimensions. Resolve conflicting versions/views explicitly; ask only when missing information materially changes scope, scale, location or destructive edits.
Prioritize silhouette, proportions and facade rhythm before ornament. Use transforms, blueprint components and generators only where they fit the reference; blueprint description/constraints can carry source links and observation/inference/unknown notes. Keep the one-survey/build/one-render workflow, with a render viewpoint comparable to the reference. Explain material approximations and unresolved uncertainty; do not invent a similarity score. Visual fidelity, including 'as close as possible', does not automatically request exact block-state auditing. mc_verify compares blocks with a frozen specification, not with a photograph.

Full exact verification is opt-in: use it only when the user explicitly requests exact block-state verification, not simply because a photo reproduction is requested, the tool is available or a build is large. Then mc_verify prepare BEFORE mc_build, check afterwards, and mc_repair from the latest comparisonId (details in those tools).
