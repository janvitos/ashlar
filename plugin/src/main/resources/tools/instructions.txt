Ashlar: tools for reading and building in a live Minecraft (Paper) server. Thirteen tools are available - load them by name when needed:

mc_status   - server/plugin health and queue length
mc_players  - online players with position and facing ("here", "in front of me", "at my feet")
mc_survey   - terrain survey of an x/z area: heightmap image plus exact numbers (min/max/median height, surface mix, largest flat zone); format:"text" for an ASCII map
mc_render   - one visual PNG check: isometric/perspective schematic block shapes and depth, or existing top/facade/slice/heightmap views
mc_build    - place blocks in bulk (cuboid fills with modes replace/keep/outline/hollow/walls, individual blocks and sign text, plus rendered lettering via `text`); primary construction tool
mc_plan - validate and preview a build without placing blocks; report site collisions, overlaps, door/bed pairing and support problems
mc_verify - opt-in exact verification: prepare BEFORE building, then check frozen eligible cells; not part of routine builds
mc_repair - repair only mismatches from a fresh comparison, guard stale edits/block entities, then recheck the whole expectation
mc_blueprint - optionally generate architectural parts or fit foundations/entrances with one bounded terrain capture; save/get/list/delete reusable blueprints with named components, palettes and repeated instances; no world writes
mc_inspect  - exact block contents of a region (statistics, per-column runs, ASCII slice, sign text)
mc_snapshot - save a region before changing it (or list saved snapshots)
mc_restore  - roll a region back to a snapshot
mc_command  - run a server console command and return its output (escape hatch)

Default lightweight workflow: mc_players only when player context/safety is needed; one mc_survey before a substantial build, reusing a recent relevant survey; mc_build; one mc_render of the finished substantial build for appearance; use isometric/perspective with tight [x,y,z] bounds when an angled exterior view helps. Tiny edits can rely on build feedback. Prefer a few bulk build calls. Do not stack mc_plan, dryRun, preflight and mc_verify on ordinary builds, repeat whole-build checks, or inspect every block by default. Stop once the requested result looks satisfactory and no concrete issue remains. All builds still receive mandatory plugin-side structural safety validation, without extra agent tool calls.
If the visual check or build feedback reveals a specific issue, inspect only the affected area and make a targeted correction, with a focused recheck if needed. If it remains unresolved, explain the issue rather than starting an open-ended verification loop. Preserve rollback protection when changing existing terrain/structures, preferably mc_build snapshot:true instead of a redundant separate snapshot call; snapshots do not back up NBT. Do not automatically restore the whole region for a small defect.
Coordinates: X east, Z south, Y up; from/to corners are inclusive.
For rotated or mirrored designs, mc_build accepts transform:{origin:[x,y,z],rotation:0|90|180|270,mirror:"none"|"x"|"z"}. All build coordinates then become local: mirror first, rotate clockwise viewed from above, translate last. States, partial filters and text geometry transform too. mc_plan, preflight:true and dryRun:true are optional escalation tools, not default steps. Use them when the user requests a preview/strict site checks or a concrete placement risk warrants analysis. Review pairing/support issues and existing-non-air changes; those may be terrain or structures. Do not run multiple equivalent analyses for reassurance. Planning does not reserve the world or simulate connections, fluids or entities. Isometric/perspective views use schematic visual cuboids and map colors, not textures or exhaustive resource-pack models. Stored connections are shown without updating them; approximate/fallback shapes and resolution reductions are reported. Camera azimuth/elevation are optional; fov is perspective-only and angled grids must be 0. Other views retain their existing flat maps. All build phases are structurally validated before the first snapshot/write.

Full exact verification is opt-in: use it when the user requests exact verification/fidelity (for example a precise photo reconstruction), not simply because the tool is available or a build is large. Development unit/native acceptance tests are never a per-build agent workflow. When exact verification is requested, call mc_verify action:prepare with the build request BEFORE mc_build, then action:check with its planId afterward. Expectations freeze keep/filter eligibility and managed sign values; they expire after two hours or plugin reload/restart. mc_repair requires the latest comparisonId and rechecks selected observed cells before snapshot/write. It never rewrites matching cells or runs a connection/neighbor pass. Exact mode includes all properties; placement mode explicitly excludes derived connections for connected builds, never orientation or chest type. Skipped/untouched cells, entities, rich sign styling and arbitrary NBT are outside scope. Flowing plans cannot be auto-repaired. Snapshots store block states only, NOT sign text or inventories; deletion/material replacement of block entities requires explicit opt-in. Review diagnostics; this is not a world lock or transactional undo.

Saved blueprints use mc_blueprint version:1 documents with flat named components and instances. mc_build accepts blueprint:{id,palette?} instead of direct fills/blocks/text, and composes component orientation, instance position/repetition and project transform. Use $role[property=value] for material bindings. Other tools still use world coordinates. Include both door/bed halves; mirrored block lettering mirrors glyphs, not sign strings.
